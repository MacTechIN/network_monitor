# ADR-0001: 트래픽 가시성 확보 방식 — Pi 게이트웨이 모드

- 날짜: 2026-10-30
- 상태: 채택 (1차). 관리형 스위치 확보 시 미러 포트 방식으로 재검토

## 맥락
- 목표: 로컬 네트워크에서 공유기를 통해 나가는 **모든** 패킷을 Pi가 수집해야 한다.
- 현장 조건 (2026-10-30 실측)
  - 공유기 192.168.45.1: Boa/0.93.15 웹서버, 80/8080 포트, 로그인 페이지만 노출. 통신사 공유기 형태로 포트 미러링 기능이 없을 가능성이 높음.
  - Pi 5: eth0 하나(1Gbps). USB NIC 없음. wlan0 미사용.
  - Pi는 공유기 DHCP로 192.168.45.162를 받고 있음. NetworkManager(netplan-eth0 연결) 관리.
  - Pi에는 nftables/iptables가 있고 dnsmasq, tcpdump는 없음. Tailscale 운영 중.
- 제약: ARP 스푸핑은 정의서 8장에 따라 금지.

## 검토한 대안
| 대안 | 결론 |
|---|---|
| 미러(SPAN) 포트 | 가장 깨끗하지만 관리형 스위치 구매 필요. 하드웨어 없음 → 보류 |
| 인라인 브리지 | USB3 기가비트 NIC 필요 → 보류 |
| 공유기 펌웨어 교체(OpenWrt) | 통신사 공유기라 불가능하거나 약정 문제 |
| ARP 스푸핑 | 금지 |
| **Pi 게이트웨이(router-on-a-stick)** | 추가 하드웨어 없이 즉시 가능. 클라이언트가 **명시적으로** Pi를 기본 게이트웨이로 받음(DHCP) → 채택 |

## 결정
1. Pi eth0을 고정 IP 192.168.45.162로 전환한다.
2. Pi에서 IP 포워딩을 켜고 ICMP redirect 전송을 끈다 (끄지 않으면 클라이언트가 Pi를 우회해 공유기로 직접 감).
3. nftables로 `LAN → 인터넷` 트래픽을 masquerade한다. 같은 L2 세그먼트에서 되돌아오는 패킷이 Pi를 거치게 하려면 NAT가 필요하다(없으면 비대칭 라우팅으로 응답 방향을 못 봄).
4. DHCP: 공유기가 "기본 게이트웨이 옵션"을 지원하면 그것을 Pi IP로 바꾼다. 지원하지 않으면 공유기 DHCP를 끄고 Pi의 dnsmasq가 DHCP/DNS 서버가 된다. 어느 쪽이든 DNS도 Pi로 보내 DNS 질의 가시성을 확보한다.
5. 캡처 지점: eth0. Suricata/tcpdump BPF는 `net 192.168.45.0/24 and not host 192.168.45.162`로 두어 **클라이언트 측 구간(원래 IP 보존)**만 잡고 NAT 이후 공유기 측 구간의 중복을 제외한다.

## 결과와 감수 사항
- 장점: 하드웨어 없이 모든 인터넷행 트래픽과 DNS가 Pi를 지남. 향후 IPS(차단)로 확장 가능.
- Pi가 **단일 장애점**이 된다. Pi가 죽으면 클라이언트는 임대 만료 전까지 인터넷 불가. 완화: 임대 1시간, 롤백 스크립트, 공유기 DHCP 재활성화 절차 문서화.
- 처리량: 입출력이 같은 NIC를 지나므로 인터넷 트래픽 최대치는 약 450~500Mbps. 일반 가정 회선에는 충분.
- 공유기 입장에서 모든 트래픽이 Pi 한 대에서 나오는 것으로 보임. 공유기의 포트포워딩/UPnP로 내부 기기에 들어오던 연결은 깨짐. 필요 시 Pi에서 DNAT로 재구성.
- 기기 간 내부(LAN↔LAN) 트래픽은 여전히 보이지 않음. 내부 확산(lateral movement) 탐지는 미러 포트나 브리지가 있어야 가능. 1차 범위에서는 인터넷 방향에 집중.
- 고정 IP/고정 게이트웨이를 직접 설정한 기기는 DHCP를 안 받으므로 Pi를 거치지 않는다. 자산 발견 단계에서 "게이트웨이 우회 기기"로 표시한다.
